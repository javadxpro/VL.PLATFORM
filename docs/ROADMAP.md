# نقشهٔ راه VL Platform

> این فایل **قفل مرحله** است. چیزی که اینجا در فاز آینده نوشته شده، در نسخهٔ فعلی
> ساخته نمی‌شود — و چیزی که در کد ساخته می‌شود، باید یکی از فازهای همین فهرست باشد.
> اگر قابلیتی لازم شد که در هیچ فازی نیست، اول به این فایل اضافه می‌شود (با دلیل)،
> بعد کد.
>
> بازبینی: ۱۳۹۵-۰۶-۲۳ · مالک تصمیم: صاحب پروژه · مجری: Agent توسعه

---

## ۰) قواعد فرود یک قابلیت (همیشه جاری، نه فاز)

1. **ستون/جدول جدید فقط با migration** در `backend/migrations.py`؛ افزودنی،
   بدون حذف، قابل‌اجرای مجدد، و در هر دو گویش (SQLite/Postgres). دادهٔ کهنه در
   همان مرحله backfill می‌شود.
2. **هر endpoint جدید پشت یک کلید در `app_info.capabilities`.** تفاوت Explore و
   Advanced *مجموعهٔ قابلیت* است، نه بک‌اند دوم و نه حساب دوم.
3. **از `Module.route`**: `auth`/`rate`/`csrf` پیش‌فرض‌هایش را نگه می‌دارد؛
   فیلتر دید (private/friends/blocked) داخل SQL نوشته می‌شود، نه بعد از گرفتن ردیف‌ها.
4. **هر فاز با تست خودش تمام می‌شود** (`tests/`) + `python tools/gen_api_docs.py`
   برای تازه‌ماندن `docs/API.md`؛ CI (pyflakes، `migrate + doctor --json`، pytest)
   سبز است.
5. **UI بخش Explore را من بازطراحی نمی‌کنم** — فقط پیشنهاد می‌دهم؛ مسیرهای
   مشخص و قابل‌فهم قلمرو صاحب پروژه است. تغییر در Advanced یا در API آزادتر است.
6. **بدون وابستگی تازه مگر لازم باشد.** هیچ Redis/broker/CDN/سرویس بیرونی به
   معماری اضافه نمی‌شود مگر فاز صریحاً بگوید (در حال حاضر: single-process + gevent).
7. **هر قابلیت باید «چرا» داشته باشد.** بدون دلیل در این فایل، وارد نمی‌شود.

## ۱) نقطهٔ شروع: چیزی که *همین حالا* در کد است

خوانده‌شده از اسکیمای مهاجرت‌شده (نه از توضیح فایل‌ها):

| حوزه | وضعیت فعلی |
|---|---|
| هویت | یک `users` واحد (username/role/status/presence) + `sessions` با انقضا و ابطال؛ `follows`, `friendships`, `user_blocks`, `user_settings` |
| بازی | `games(slug, name, icon, cover, platforms, genre, is_featured, discover_provider)` |
| گیمینگ کاربر | `user_games(status, hours_real, achievements, last_played_at)`, `gaming_profiles`, `gaming_activity` |
| اتاق/سرور | `game_rooms(visibility, password_hash, max_players)` + `game_room_members/invites`؛ `lan_hosts`, `server_players`, `server_follows`, `server_status_log` + discovery |
| گروه | `groups`, `group_members`, `group_invites`, `group_bans`, `group_seen` |
| محتوا | `posts(file_path, file_type, hashtags, visibility)` + comments/likes/reactions/views/saves، `stories`, `chat_threads`, `messages` |
| Community/امانت | `reports`, `moderation_actions`, `notifications`, `search_index` |

**هنوز نیست** (و عمداً ساخته نشده): موجودیت `clips`، `video_templates`، جدول
`achievements`، `reputation`، بخش‌های صفحهٔ بازی (Guides/Mods/Maps/Events)،
catalog بازی‌های بیرونی.

## ۲) فازها

### P0 — زیرساخت و سازگاری (انجام‌شده)
لایهٔ سازگاری با مسیرهای نسخهٔ ۳، `db.py` دو-گویش، migrations v1…v10، CLI
عملیاتی، Docker/Render/Procfile هم‌راستا، CI، `docs/security.md`.
دلیل وجود: بدون این‌ها هر فاز بعدی روی پایه‌ای می‌نشیند که با یک deploy می‌شکند.

### P1 — VL ID (همین مرحله) ✅
یک شناسهٔ عمومیِ پایدار و **غیرقابل‌شمردن** روی همان حساب واحد: `users.vl_id`
با migration `0011:vl_identity`، backfill ردیف‌های موجود، unique index، فرمت
`VL-XXXX-XXXX` (Crockford base32)، و نمایش در `/api/auth/me` + پروجکشن `users`.

دلیل وجود: تا وقتی تنها ارجاع عمومی به کاربر، `users.id` ترتیبی است، هر چیزی که
بعداً به «هویت» وصل می‌شود (reputation، achievements، clip author، سرور مالکیت)
یا رمزنگاری‌شدهٔ ترتیب ثبت‌نام را لو می‌دهد یا باید بعداً مهاجرت کند — و مهاجرتِ
کلید بیرونی روی دادهٔ واقعی، گران‌ترین کار ممکن است. پس این یکی *همین حالا* ارزان
و بعداً گران است.
خارج از این فاز: جست‌وجو/lookup با VL ID، تغییر آن، endpoint تازه، صفحهٔ پروفایل
عمومی بر اساس آن.

### P2 — Game Pages (بعدیِ پیشنهادی)
صفحهٔ اختصاصی هر بازی: `game_id` + بخش‌ها. کمینهٔ سرور-ساز: یک جدول
`game_sections(game_id, kind, title, slug, body, author_id, visibility)` که
Guides/Mods/Maps/Events همه در آن می‌گنجند، و فهرست‌ها از جدول‌های موجود
(`servers`، `players`، `groups`، `clips`) با فیلتر `game_id` ساخته می‌شوند.

دلیل وجود: «هر بازی یک خانه دارد» تنها چیزی است که VL را از یک شبکهٔ اجتماعی با
برچسب بازی جدا می‌کند؛ و تنها دلیلی که کاربر قدیمی را از تلگرام/اینستاگرام به اینجا
می‌کشاند.
تصمیم باز (مالک): کدام بخش‌ها در نسخهٔ اول می‌آیند — پیشنهاد من: Servers + Clips +
Guides؛ Mods/Maps/Events بعداً.

### P3 — کلیپ و الگوی ویدئو، با کپی‌رایت از روز اول
موجودیت `clips(id, game_id, author_id, source_path, kind, duration_ms, ownership,
source_url, review_state, …)` + `video_templates` (قالب‌های آماده: intro/outro/
زیرنویس/برش). `ownership` از همان اول ثبت می‌شود (خودت‌ساخته / از بازی ضبط‌شده /
بیرونی) حتی اگر هنوز بازبینی انسانی نداشته باشیم.

دلیل وجود: ویدئو پرهزینه‌ترین محتوای این پلتفرم است (فایل، ترافیک، ادعا). اگر
مالکیت محتوا ثبت نشود، بعداً نمی‌توان به‌درستی حذف/اعتبارسنجی/امتیازدهی کرد و
هزینهٔ عقب‌ماندگی روی هر فایلِ موجود می‌افتد.
تصمیم باز (مالک): خوداظهاری کافی است یا صف بازبینی لازم است؟ (کیفیت: محدودیت
اندازه/مدت و بی‌کیفیتی‌زدن — فعلاً `VOLEXTURN_MAX_VIDEO_MB`.)

### P4 — دستاوردها و اعتبار (Achievements / Reputation)
`achievements` + `user_achievements` + `reputation(user_id, score, signals_json)`؛
همه کلیدشان یا `vl_id` است یا `user_id` (انتخاب: `user_id` داخلی، `vl_id` عمومی).

دلیل وجود: بدون سیگنالِ اعتبار، Pages/Servers/Clips بی‌کیفیت و پر از اسپم می‌شوند؛
این قابلیت «پلیس» نیست، رتبه‌بندیِ دیده‌شدن است.
بی‌رحمانه ساده نگه داشته می‌شود: شمارش + قانون ثابت، نه ML.

### P5 — Explore / Advanced رسماً
هر دو حالت روی **یک حساب**؛ `app_info.capabilities` مجموعهٔ قابلیت هر حالت را
می‌دهد (Advanced: ابزارهای مدیریتی، فیلترهای عمیق، exports، CLI‌-مانندِ UI).
بخش Explore: فقط بازچینش تجربهٔ ورود، نه تغییر مدل داده.

### P6 — ابزارهای Advanced (لیست را مالک می‌نویسد)
پیش‌نهاد من برای شروع (۵ تا، نه بیشتر): moderation پیشرفته/صف گزارش‌ها،
analytics سرور و اتاق، export داده کاربر، bulk upload با متادیتا، مدیریت
گروه‌های عمومی/دسته‌ها. هرکدام که دلیلش ننویسد، حذف.

### P7 — catalog بازی‌های بیرونی
`games.discover_provider` از قبل هست؛ اتصال به یک سرویس بیرونی (نه CDN/سرویس
پولی بدون ضرورت) فقط با یک provider قابل‌غیرفعال و کش محلی.

## ۳) عمداً نمی‌سازیم (تا اطلاع بعدی)

| مورد | چرا نه |
|---|---|
| پیشنهاددهندهٔ ML / رتبه‌بندی یادگیرنده | داده نیست؛ با سیگنال‌های P4 قابل تقلید است |
| E2EE برای چت | تهدید مدلِ LAN/اعتماد محلی نیست و کلیدمدیریتی‌اش کل UX را عوض می‌کند |
| پرداخت/اشتراک/فروش | خارج از هدف اکوسیستم در این برهه |
| اپ نیتیو موبایل | SPA + PWA روی همان endpoint؛ دو‌بکه‌شدن API را می‌خواهد |
| تفکیک به میکروسرویس | room/presence در حافظهٔ یک پروسه است؛ تفکیک یعنی شکستن همین |
| Redis/broker/جست‌وجوی خارجی | تا وقتی `search_index` + SQLite/PG جواب می‌دهد |
| فدراسیون/ActivityPub | مدل دید و بلاک محلی است؛ بعد از P4 معنی پیدا می‌کند |

## ۵) تصمیم‌های باز برای مالک (منتظر پاسخ)

1. لیست دقیق ابزارهای Advanced (P6) — وگرنه P5 فقط یک نام باقی می‌ماند.
2. کپی‌رایت P3: خوداظهاری + امکان گزارش، یا صف بازبینی؟
3. آیا کاربر می‌تواند با VL ID جست‌وجو/آیدی‌فای شود، یا فقط نمایش داده می‌شود؟
   (در P1 فقط نمایش.)
4. slug سه بازی Hamedis (فوتبال خیابونی ایران / زمین چمن / مسابقه واقعی) چه باشد —
   `games.slug` از قبل یکتا و خواناست.
5. گروه‌های عمومی پیش‌فرض چه دسته‌بندی‌هایی دارند (پیشنهاد: per-game + general + clips).
6. دادهٔ نصب‌های قدیمی (`admin123`, DB نسخهٔ ۳) مهاجرت کند یا نصب تازه لازمه؟
